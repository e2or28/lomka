# tests/ — проверки без окна

```bash
tools/test.sh     # всё разом, около секунды
tools/check.sh    # плюс аудит синтаксиса, тесты инструментов и стенд
```

Симуляция отделена от представления (правило 2 из `../docs/PLAN.md`) в том
числе ради этого: тесты гоняются headless, на каждый коммит, через
pre-commit хук.

**Этот каталог не нужно читать, когда работаешь над игрой.** Достаточно
знать, что здесь лежит и что оно стережёт — таблица ниже. Открывать сами
файлы стоит, только когда правишь тест или разбираешь его падение.

## Три класса тестов

У каждого файла в шапке написано, к какому классу он относится. Класс
отвечает на один вопрос: **что делать, когда тест покраснел.**

**Инвариант** — чинить код, тест не трогать. Это правила из
`../docs/PLAN.md`, которые держат онлайн-кооп и сохранения: изоляция
потоков случайности, круговорот сейва, порядок фаз в стеке, детерминизм
реплея. Нарушение всплывает не сразу, а рассинхроном через месяц, поэтому
подгонять такой тест под новый код нельзя никогда.

**Поведение** — переписать вместе с игрой. Бой, враги, баллистика, поза,
оружие. Эти правила меняются по замыслу, и красный тест здесь чаще значит
«замысел изменился», чем «сломалось». Переписал ожидание — нормальная
работа.

**Эвристика** — сначала посмотреть глазами. Пока такой ровно один:
`test_art_facing.gd` угадывает сторону взгляда по цвету пикселей. Новый
набор спрайтов может уронить его, не сломав ничего.

`framework/arena.gd` — оснастка боевых тестов: собрать комнату, прогнать
тики, выстрелить. `framework/test_case.gd` — база,
`framework/reference_run.gd` — эталонный забег для фикстуры, `fixtures/` —
эталонный сейв в гите.

`tools/test_checks.py` проверяет shell-обёртки на подставном движке:
аварийный выход, ошибка скрипта при успешном сентинеле, потерянный сентинел
и распространение ошибки из `status.sh`. Запуск отдельно:
`python3 -m unittest discover -s tests/tools -v`. Внешних зависимостей нет.

## Как написать тест

Файл `test_*.gd`, наследует базу, методы возвращают `true`:

```gdscript
extends "res://tests/framework/test_case.gd"

func title() -> String:
    return "что проверяем"

func _test_свойство() -> bool:
    eq(actual, expected, "что пошло не так")
    return true
```

Список методов харнесс собирает интроспекцией — диспетчер писать не надо.
Про обязательный `return true` и про сторож в `run_all.gd` — раздел
«Ловушки» в `../CLAUDE.md`.

## Три правила

**Тест пишется под названный риск** из `../docs/PLAN.md` или
`../docs/DECISIONS.md`, а не на всякий случай. У каждого файла в таблице
выше такая строчка есть.

**Циклы агрегируются.** Проверка по 48 действиям собирает расхождения в
список и падает один раз, а не сыплет полсотней одинаковых строк.

**Подготовка идёт через `framework/arena.gd`.** Своя копия «прогнать N
тиков» в каждом файле — это не лишние строки, а несколько мест, где может
разъехаться смысл одного и того же действия. Не хватает чего-то — добавь
в арену, а не рядом с тестом.
